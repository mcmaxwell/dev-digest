# DevDigest

Local-first AI PR review: import a GitHub PR, run an LLM agent review, get
grounded findings. Course starter — lessons L01–L08 add features on top
(lesson list in README.md).

5 standalone packages — **no monorepo workspace**: each folder has its own
package.json + lockfile; cross-package code is shared only via tsconfig path
aliases, never published modules.

## Stack

Node ≥ 22 · pnpm ≥ 10 · TypeScript · Vitest
Server: Fastify 5 + Drizzle ORM + Postgres/pgvector (Postgres in Docker; apps on host)
Client: Next.js 15 App Router + React 19 + TanStack Query + next-intl
Engine: pure TS, LLM via injected provider (OpenAI / Anthropic / OpenRouter)

## Commands

```sh
./scripts/dev.sh                 # full stack from zero (Postgres + API :3001 + web :3000)
cd server && pnpm db:migrate     # migrations do NOT run on server boot
cd server && pnpm db:seed        # idempotent demo data (acme/payments-api, PR #482)
cd <pkg>  && pnpm test           # per-package; server splits unit vs *.it.test.ts
./scripts/e2e.sh                 # hermetic browser e2e (isolated stack, safe anytime)
```

## Map

```
server/         @devdigest/api  — Fastify API; modules/{repos,pulls,agents,reviews,
                repo-intel,polling,settings,workspace}; DI adapters in adapters/
client/         @devdigest/web  — app/{repos,agents,settings,onboarding}; hooks in
                src/lib/hooks/*; feature logic in colocated _components/
reviewer-core/  engine: diff + repo map → prompt → LLM → grounded findings
mcp/            local MCP server (stdio) for editor agents: 5 tools, reaching
                the API over HTTP only; own process, zod 4, no shared aliases
e2e/            deterministic agent-browser flows (JSON specs, no LLM, no keys)
docs/           agent-prompts/ (built-in reviewer prompts) · specs/ (lesson specs)
```

## Rules (non-default)

- `@devdigest/shared` (Zod contracts) has TWO physical copies:
  `server/src/vendor/shared` (canonical — server + reviewer-core alias to it)
  and `client/src/vendor/shared` (client's own copy). Changing a contract means
  updating BOTH, or client and server silently drift.
- reviewer-core is pure: no DB, no fs, no GitHub imports; LLM only via injected
  `LLMProvider`. It never emits JS — server consumes its TS source by alias.
- Server route validation is schema-first (zod via fastify-type-provider-zod);
  never hand-parse `req.body` in handlers.
- Server tests: DB-backed files MUST use the `*.it.test.ts` suffix (they start
  real Postgres via testcontainers); everything else stays hermetic.
- Secrets live in `~/.devdigest/secrets.json` (via `LocalSecretsProvider`) with
  env fallback — never in git or the DB. `GITHUB_TOKEN` is canonical.

## Do not touch

- `server/clones/**` — runtime checkouts of imported repos; never edit or commit
- `server/src/db/migrations/**` — generated; change schema.ts then `pnpm db:generate`
- `client/src/vendor/ui/**` — vendored UI kit
- `.env` files — secrets; edit `.env.example` instead
- NEVER `docker compose down -v` to "fix" the dev DB — `-v` deletes the
  `devdigest_pgdata` volume with every imported repo and review

## Read when…

- …you need the structure and nothing else (package layout, test lanes, boundary
  rule names, the two contract copies, do-not-touch, environment traps) →
  `.claude/repo-facts.md`. Generated by `scripts/repo-facts.sh`; regenerate it
  when a package script, a module, a contract file, or a depcruise rule changes.
- …changing the review pipeline, prompts, or grounding → `reviewer-core/README.md`
- …adding/changing API routes, DB schema, or adapters → `server/README.md`
- …touching indexing, the repo map, or the Indexed badge → `server/src/modules/repo-intel/README.md`
- …working on UI routes, hooks, or components → `client/README.md`
- …changing the MCP tools, their descriptions, or the token budget →
  `mcp/README.md`, then `mcp/AGENTS.md` (tool descriptions are taxed in every
  session, so their wording is a deliberate decision, not a refactor)
- …writing or fixing tests (any package) → `TESTING.md`; browser flows → `e2e/README.md`
- …editing built-in reviewer agent prompts → `docs/agent-prompts/README.md`
- …implementing a lesson feature → its spec in `docs/specs/`
- …writing or reviewing a spec (format, EARS criteria, naming) →
  `docs/specs/README.md`; the `specreator` agent writes them, create-only
- …starting any task inside a package → that package's `AGENTS.md`, then its
  `INSIGHTS.md` (treat entries as high-confidence guidance)

## After finishing a task

Use the `engineering-insights` skill: capture non-obvious lessons into the
touched module's `INSIGHTS.md` as they surface during the task, and run its
wrap-up check before finishing — do not skip it. Trivial tasks (no problem,
solution, or discovery) are exempt.

`workflow-retro` is the separate, **manually invoked** counterpart for lessons
about the agents rather than the code (ledger: `docs/retro/ledger.md`). Never
run it on your own initiative, not even after a large multi-agent task - it
starts only when the user asks for it.
